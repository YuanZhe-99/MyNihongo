# 内容撰写

内容库如何长大：哪些由人手写、哪些由模型写、各自由什么来把关，以及这一切都保证不了什么。

[`content-catalog.md`](content-catalog.md) 讲这些文件是什么，本文讲新文件怎么来。

## 它要解决的问题

词汇由 JMdict 与 JLPT 词表生成，因此一次就到齐了：五个级别共 7,744 个词。其余的没有。语法是手写的，只到 N5。中文释义由机器生成，也只到 N5。例句在 7,744 个词里只有 24 个。

剩下的工作不难，只是量大：约 600 个语法点、7,000 条释义、7,700 个句子。这些由模型代理分批写。

## 循环

```
draft_inputs.dart  →  代理写草稿  →  content_gate_test  →  merge_drafts.dart
```

1. **`dart run tool/draft_inputs.dart <kind> --level N4 [--batch 300]`** 在 `tool/content/drafts/` 下写出批次文件。每个批次**就是**尚缺内容的清单，因此两个代理不会撞车，合并之后重新生成也只会得到更少的批次。
2. **代理在输入旁边写草稿**，`n4-01.input.json` → `n4-01.json`。它从不运行构建，也从不运行测试。
3. **`CONTENT_DRAFT=<path> flutter test test/content_gate_test.dart`** 判定草稿，并一次性列出其中**全部**问题，每条都点名 id、句子和该怎么改。一个批次通常一轮就能修完。
4. **`dart run tool/merge_drafts.dart <kind> [--level N4] <drafts...>`** 把批次折进已发布的文件。它不作任何判断：判断都在第 3 步做完了。

两个词汇叠加层在合并后还要跑 `dart run tool/import_vocab.dart --overlay-only`，它把叠加层折进生成的目录，不需要那 117 MB 的 JMdict 本体。然后跑 `dart run tool/convert_zh_tw.dart` 写出繁体——永远如此，因为繁体是生成的，从不撰写。

新增的语法文件还要加进 `ContentRepository.grammarAssets`。除此之外应用里没有别的地方需要改动。

## 五种草稿

| 种类 | 批次大小 | 写入 |
|---|---|---|
| `gloss` | 300 个词 | `vocab_zh.json`，中文叠加层 |
| `examples` | 150 个词 | `vocab_examples.json`，例句叠加层 |
| `grammar` | 25 个语法点 | `grammar/<level>.json` |
| `units` | 整个级别一次 | `lessons/<level>.json` |
| `drills` | 一次一个大問 | `drills/<level>-<section>.json` |

**语法 id 在写任何内容之前先定死。** `grammar-inventory` 一次产出该级别的 id 与句型清单，并对照每一个已发布的 id 检查。id 是兼容契约——一条进度记录就以它为键——所以两个批次为不同的语法点发明同一个 slug、或为同一个语法点发明两个 slug，是唯一一种事后无法补救的错误。

**一个级别的单元整体规划**，不分批，因为让这条路径成其为路径的性质是：该级别的每个语法点恰好属于一个单元。互相看不见的批次做不到这一点。

**一个练习题批次是一个大問或几个，绝不会是半个大問。** 批次生成器按题目数量切分，但绝不切开一个大問，因为同一个大問的题目共享一种风格，阅读与听力还共享文章：两个代理各写一半，会产出对不上的两半。

练习题批次也是唯一一种输入为**两个**文件的草稿。该级别的词汇与语法放在一个单独的 `<level>-<section>.resources.json` 里，由每个批次点名引用，而不是被复制进每一个批次：一个级别的常用词汇有好几千行，逐批次重复一遍会把一个三十道题的请求变成一兆字节的同一份清单。

`drills` 的合并是往已发布的文件里**追加**，而不是跳过已经存在的东西——一个部分要经过好几个版本才填满，而每个批次都是新题目，不是旧题目的更好版本。重复的 id 是致命错误而不是被跳过：题目 id 正是「已经问过」所依据的记忆方式，而同一个 id 下有两道题会让它变成「文件里碰巧先列的那一道」。

**情景是写进一个已经存在的单元里的**，而不是作为独立草稿合并：`merge_drafts units` 会重写整个级别的文件，再跑一遍带来的改动比加一段对话大得多。要给这样加进去的情景过门禁，把已发布的文件反向变回草稿——去掉生成的 `zh_TW`，包成 `{"kind": "units", ...}`——再对它运行门禁。

## 门禁检查什么

每一条规则都是已发布测试本来就对目录施加的规则，只是提前执行，让批次在合并前而不是合并后失败：

- **日语能被解析**，且不含未知 token，用的都是应用自带的词。这是 `sentence_analyzer_test` 的规则，也是最强的一条：句子里用了目录之外的词就无法分词，于是句子实验室、测验与交叉链接会一起失效。
- **不依赖更难的级别。** `content_links_test` 的规则：N4 的句子不能需要一个 N2 的词。
- **读音与句子对得上**，经由振假名对齐器。这既是显示上的要求，也是「这条读音确实属于这个句子而不是它的某个早期版本」的最廉价检查。
- **`en` 与 `zh` 齐全**，且**绝不写 `zh_TW`**——那是生成的，手写的会让 `content_zh_tw_test` 失败。
- **id 是新的、格式正确、且在批次内与全部已发布内容中唯一。**
- **语法点能在自己的例句里被找到**，否则分析器匹配不到它，测验也无法就它出题。
- **一道题有四个互异的选项和一个合法的答案下标**，因为两个相同的选项就是两个正确答案。
- **情景的分支落在自己的脚本之内**——`after` 是已显示的行数，所以必须在 1 到对话行数之间——**并且恰好有一个选项被标为正确**，因为结尾的统计只数一个。
- **释义是中文**：不含假名、不残留英文、短到能放进一行列表。

## 什么都没检查的部分

**日语是否自然，译文是否忠实。**

没有测试能做到。门禁证明的是一个句子*可解析、级别合适、读音正确*；它无法证明这个句子*地道*。一个通过了上面全部规则的模型生成句，仍然可能是母语者不会说的话。

所以文件本身把这一点写明。每个模型生成的文件都带着 `"source": "model-authored (Claude), unreviewed"`，`vocab_zh.json` 每一行都保留 `reviewed: false`，而 `content-catalog.md` 里「日文由人检查」那条规则被改写为它实际所是的期望，而不是对已发布内容的断言。

这是一个有意的决定，因为另一条路是只发布 N5 而没有其余。它记在 `PLAN.md` 的决策日志里，而「谁来审校」这个开放问题仍然开放。

## 许可

模型生成的内容与为本应用撰写的其他一切一样，随应用采用 GPL-3.0。它不派生自任何受版权保护的来源，提示词也没有要求复现任何来源。每个文件的 `source` 字段记录它是怎么来的，这正是 `content-catalog.md` 里那张许可表所需要的。
