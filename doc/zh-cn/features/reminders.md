# 提醒

每天一条本地通知，在学习者打开它之前一直是关闭的，内容是真正在等着他们的东西。整件事没有任何一处接触网络。

## 塑造其余一切的那条规则

**权限由开关请求，别处一概不请求。**

`ReminderService.init()` 在每台设备上都从 `main` 运行，准备插件与时区数据库。它从不请求任何东西。请求只发生一次，在 `setReminderEnabled(true)` 内部，就在学习者打开提醒的那一刻；若被拒绝，开关保持关闭，并附一行说明系统已为本应用关闭通知。

之所以写下这条，是因为这里已经出过一次错。M2.4 曾发布过一个一打开设置就请求麦克风的版本，现在有一条测试断言 `init` 发起的权限请求次数为零。

iOS 与 macOS 的初始化设置显式关闭了 alert、badge 与 sound 三项请求，而不是靠不写来关闭——因为插件的默认值会在初始化时把三项全部请求一遍。

## 它说什么

计划由纯函数 `planReminders` 根据时间、进度文件与路径算出。它不读任何偏好、不发布任何东西，这正是它的措辞与时机能在一台没有通知功能的机器上被精确测试的原因。

| 情形 | 正文 |
|---|---|
| 今天有到期项 | 有多少项 |
| 无到期项、有已解锁的单元 | 那个单元的名字 |
| 两者都没有 | 一句普通的招呼 |

一次排七天，因此一台一直没被打开的手机仍会被提醒一周。只有第一天带数字：没有谁能知道周四会有多少项到期，而一个悄悄错了的数字比没有数字更糟。

**当天已过的时间点从明天开始。** 晚上九点打开开关，不能触发当天早上八点的提醒。

开关、时间或进度文件一变，计划就重算，并且是替换而非追加——否则一天学两次的学习者会攒下一周的过期提醒。

## 两个平台，两种承诺

| | Android 与 iOS | Windows、macOS、Linux |
|---|---|---|
| 谁来触发 | 操作系统 | 运行中的应用里的一个定时器 |
| 应用关闭时 | 仍会提醒 | 不会提醒 |
| 权限 | 由开关请求一次 | 不需要 |

桌面路径每天至多发布一次，以本地日期记在 `storage_config.json` 里，因此一台一直开着的机器不会连着一小时每分钟弹一次。那份更弱的承诺写在设置的副标题里，而不是被含糊过去。

两者都不支持的平台根本不显示这个开关。一个什么都做不了的开关比没有开关更糟。

## Android 相关

`POST_NOTIFICATIONS` 在开关处请求。`RECEIVE_BOOT_COMPLETED` 是让排程在重启后仍然存在的东西；没有它，重启过的手机就不再提醒，而且没有任何地方说明为什么。

**`SCHEDULE_EXACT_ALARM` 是有意不申请的。** Android 把它视为高权限，一条学习提醒不配拥有它，而 `inexactAllowWhileIdle` 能把提醒送到整点前后几分钟内——一句招呼本来就是这样的东西。

## 偏好

三项都是设备本地的，没有一项同步。手机和笔记本想要的提醒时间不同，而习惯是长在某台设备上的。

| 键 | 缺省 | 存储 |
|---|---|---|
| `reminderEnabled` | 关 | 仅在开启时写 `true` |
| `reminderTime` | 20:00 | 仅在不同于缺省时写 `"HH:mm"` |
| `lastReminderDate` | — | 仅桌面，本地 `YYYY-MM-DD` |

## 隐私

通知在设备上由进度文件组装，并由设备显示。没有任何文本、计数或时间离开设备。隐私政策里写明了这一点。
